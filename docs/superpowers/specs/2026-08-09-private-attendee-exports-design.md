# Private Attendee Exports Design

## Status

Approved with the 2026-08-09 privacy, concurrency, and recovery hardening
revisions. Implementation has not started.

## Goal

Add a private attendee export workflow that is limited to authorized event
organizers and platform administrators, requires recent session-bound
reauthentication, authorizes every selected field, produces one short-lived
audited artifact, and leaves only a payload-free audit tombstone after expiry.

The workflow never exposes answer ciphertext, consent evidence, erased or
retention-expired values, persistent storage URLs, export data, or selection
filters to staff, scanners, public endpoints, QR payloads, or operator surfaces.

## Fixed launch limits

- Reauthentication proof lifetime: five minutes.
- Export artifact lifetime: at most 24 hours from request and never later than
  the earliest `retain_until` of any included answer or revision.
- Download authorization URL lifetime: at most two minutes and never beyond the
  export's own expiry.
- Processing lease: 15 minutes; a stale attempt may be reclaimed.
- Maximum generation attempts: three.
- Maximum selected columns: 100.
- Maximum emitted rows: 250,000.
- Maximum generated bytes: 512 MiB.
- Query batch size: 1,000 rows.
- Launch format: deterministic UTF-8 RFC 4180 CSV, format version `csv_v1`.

Exceeding a generation limit fails with a controlled code and asks the organizer
to narrow the filters. A future multipart export is a separate design; launch
does not silently truncate data.

## Architecture

Use a dedicated command pipeline:

- `Core::Reauthentication::Issue` verifies `current_user`'s fresh password and
  issues an opaque proof bound to the current authentication-session JTI and a
  single purpose.
- `Core::Reauthentication::Consume` atomically validates and consumes the proof.
- `Ticketing::Exports::Request` authorizes and fingerprints the request. Exact
  idempotent replay returns the existing export without reading, validating, or
  consuming another proof.
- `Core::Outbox::Publish` records `ticketing.attendee_export.requested` in the
  request transaction; the existing Ticketing outbox handler enqueues generation.
- `Ticketing::Exports::Generate` claims a bounded processing lease, reauthorizes,
  builds the artifact, attaches it, and finalizes only while the request remains
  valid.
- `Ticketing::Exports::AuthorizeDownload` consumes a fresh download proof,
  reauthorizes, audits URL issuance, and returns a short-lived bearer URL.
- `Ticketing::Exports::InvalidateForEvent` makes every active derived artifact
  for an event non-downloadable and publishes
  `ticketing.attendee_export.purge_requested` before source answer erasure
  commits.
- `Ticketing::Exports::Expire` purges storage and replaces the request payload
  with digests, leaving an immutable audit tombstone.

Controllers load records, authorize the endpoint, invoke one command/query, and
render typed results. They never select answers, generate files, implement
idempotency, or create audit rows directly.

## Reauthentication proofs

Create `Core::ReauthenticationProof` with:

| Column | Rules |
|---|---|
| `user_id` | Required FK to the authenticated user |
| `session_jti_digest` | Required HMAC-SHA-256 digest of the current access-session JTI |
| `purpose` | `attendee_export_request` or `attendee_export_download` |
| `factor_type` | Launch value `password`; future factors require an allowlisted verifier |
| `token_digest` | Required unique HMAC-SHA-256 digest; raw token is returned once and never stored |
| `issued_at`, `expires_at` | Required; expiry is exactly five minutes after issue |
| `consumed_at` | Optional; present only after successful use |
| timestamps | Required |

Database checks enforce the purpose/factor allowlists, digest shape, ordered
times, maximum proof lifetime, and `consumed_at >= issued_at` when present.
Indexes cover unique token digest and `(user_id, purpose, expires_at)`.

`POST /auth/reauthenticate` remains authenticated. It never accepts a user
identifier: it calls `current_user.authenticate(password)`, requires the user to
remain active, binds the proof to the current decoded access-token JTI, and
returns the opaque token with `Cache-Control: no-store`. The controller obtains
the JTI from a memoized authenticated token payload exposed by
`Core::Authenticatable`; it does not decode the token a second time.

`Core::Reauthentication::Throttle` uses the shared cache to allow at most five
failed password checks per user/session in 15 minutes and 30 total issuance
attempts per IP in one hour. Counter keys use purpose-separated HMACs rather than
raw user, session, or IP values. Throttling returns a generic `429`; failed
password checks otherwise return one generic response, never issue a proof, and
record only controlled security metadata. Raw passwords and proof material are
filtered before any request logging. There is no new database table or global
account lockout that an attacker could use to deny the user access.

Consumption performs one conditional update under lock where digest, user,
session digest, purpose, unconsumed state, and unexpired window all match.
Invalid, expired, session-mismatched, and already-consumed proofs return the same
controlled `invalid_reauthentication_proof` response and never reveal which
condition failed. Account deactivation or session revocation makes the proof
unusable because consumption rechecks the user and JTI. Any password-reset flow
must revoke all of that user's authentication sessions; it must not rely on
proof expiry alone.

## Authorization and visibility

Add explicit permission codes:

- `attendee_export.request` for lifecycle metadata and non-contact standard fields;
- `attendee_export.contact` for the registration user's current email and phone;
- `attendee_export.dietary` for dietary questions;
- `attendee_export.accessibility` for accessibility questions.

Default seed grants are exact: `SUPER_ADMIN` and `ADMIN` receive all four;
`ORGANIZER` receives request and contact; `CORE_ADMIN`, `SUPPORT`, and `USER`
receive none. Dietary/accessibility access is added only through an explicit
custom/admin role assignment. An event manager who lacks
`attendee_export.request` remains denied; granting a global export permission
never expands the events made manageable by the event authorization resolver.

`Ticketing::AttendeeExportPolicy` requires both the relevant permissions and
event manageability through `Events::AuthorizationResolver.manageable_catalog_events`.

- platform administrators may manage any event;
- primary/co-organizer owners and admins, plus active event managers, may request
  only for manageable events and only when separately granted the required
  export permission;
- a staff/scanner assignment never grants export access; a separate platform
  administrator or owner/admin/manager authority still takes precedence;
- show and download are limited to the original requester or a platform
  administrator, and both must still pass current event and field authorization;
- dietary, accessibility, and contact fields require their narrow permission.

Request, generation, show, and download authorization all recheck current
permissions. Losing access makes the export unavailable and generation fails or
expires safely. Internal platform audit access is separate and never returns the
artifact or selectors.

## Export field contract

`Ticketing::Exports::FieldRegistry` is the only source of built-in fields,
extractors, headings, permissions, and row-mode compatibility. Launch built-ins:

| Selector | Permission | Row mode |
|---|---|---|
| `registration_id` | `attendee_export.request` | both |
| `registration_status` | `attendee_export.request` | both |
| `ticket_type_id` | `attendee_export.request` | both |
| `selected_event_date_id` | `attendee_export.request` | both |
| `package_unit_number` | `attendee_export.request` | admission only |
| `admission_position` | `attendee_export.request` | admission only |
| `registration_user_email` | `attendee_export.contact` | both |
| `registration_user_phone` | `attendee_export.contact` | both |

Both contact selectors read the canonical `registration.user` at generation
time. In admission mode they repeat that registration user's contact on every
derived admission row; they never claim to identify the companion or assigned
slot subject. Contact is therefore generation-time mutable data, not part of the
append-only answer cutoff. Assigned-attendee contact selectors are not launch
fields and may be added only after the downstream admission-slot assignment
model exists with its own authorization, retention, and semantic contract.

Question selectors use `question:<registration_form_id>:<question_key>`. The
resolver considers only immutable submitted form versions belonging to the
event. `FieldRegistry` computes a canonical semantic fingerprint from `key`,
`type`, `response_scope`, `sensitivity`, normalized `label`, normalized
`help_text`, `required`, canonically ordered option keys and labels, and
canonically ordered `validation_rules`. Every historical question matched by one
selector must have the same fingerprint. `position`, timestamps, database IDs,
and form-version IDs are deliberately excluded because they do not change answer
meaning. A mismatch fails with `field_definition_conflict`; values whose prompt,
choice meaning, requiredness, validation, scope, type, or sensitivity changed are
never merged. Registrations whose submitted version lacks that selector emit an
empty cell.

Text normalization applies Unicode NFC, strips leading/trailing whitespace, and
collapses internal Unicode whitespace runs to one ASCII space. Options are sorted
by immutable option key before hashing, so display reordering alone is compatible
but changing an option key or normalized label is not. Validation objects use
recursively sorted string keys and canonical JSON scalar/array encoding; array
order remains significant except `allowed_option_keys`, which is sorted because
the model defines it as a membership set.

Standard questions require `attendee_export.request`; dietary and accessibility
questions require their corresponding permission. A registration-row export
rejects admission-scope questions. There is no caller-supplied extractor,
heading, SQL expression, arbitrary JSON path, or formula.

## Row modes

Every request selects exactly one row mode:

- `registration`: one row per registration; only registration-scope questions
  and built-ins compatible with registration mode are permitted.
- `admission`: one row for every immutable
  `(registration_id, package_unit_number, admission_position)` coordinate;
  registration-level values repeat, and admission-scope values populate their
  matching coordinate.

Admission rows derive from the registration's immutable `package_quantity` and
`admissions_per_unit_snapshot`; ticket issuance is not required. `row_count`
means emitted CSV data rows, excluding the header.

## Request filters and reasons

The launch filter object has only these optional keys:

- `ticket_type_ids`: unique UUID array, maximum 100;
- `access_event_date_ids`: unique UUID array, maximum 100; and
- `registration_statuses`: unique subset of `pending_payment`,
  `pending_approval`, `waitlisted`, `offered`, `confirmed`, `rejected`,
  `cancelled`, and `expired`.

Every referenced ticket type and date must belong to the route event. A date
filter includes a registration when its choose-one selected date is requested or
its fixed/multi-day product access intersects a requested date; it never treats a
null `selected_event_date_id` as lack of multi-day access. Multiple values within
one filter use OR, while different filter keys combine with AND. Omitted or empty
filters mean all authorized rows in the cutoff-bounded event cohort. No
client-supplied time range, SQL predicate, search expression, sort, or arbitrary
JSON condition is accepted at launch.

`reason_code` is one of `event_operations`, `attendee_communication`,
`dietary_accommodation`, `accessibility_accommodation`, `customer_support`, or
`legal_compliance`. A reason records purpose but never grants a field permission;
for example, choosing `dietary_accommodation` does not authorize dietary answers.

## Attendee export data model

Create `Ticketing::AttendeeExport` with:

| Column | Rules |
|---|---|
| `event_id`, `requested_by_id` | Required FKs |
| `status` | `pending`, `processing`, `ready`, `failed`, `expiring`, or `expired` |
| `row_mode` | `registration` or `admission` |
| `format_version` | Launch value `csv_v1` |
| `field_keys` | JSONB array required before tombstoning, maximum 100 normalized selectors |
| `filters` | JSONB object required before tombstoning; exact ticket-type/date/status contract above |
| `field_set_digest`, `filter_digest` | Required versioned HMAC-SHA-256 digests retained permanently |
| `reason_code` | Required allowlisted business reason |
| `data_cutoff_at` | Required fixed upper bound for source-row existence |
| `row_count` | Optional nonnegative; required when ready |
| `file_sha256` | Optional 64-character digest; required when ready |
| `idempotency_key_digest`, `request_fingerprint` | Required HMAC-SHA-256 idempotency/request evidence |
| `digest_key_version` | Required identifier for the platform HMAC key version used by retained request digests |
| `processing_started_at`, `attempt_count` | Lease/recovery evidence; attempts `0..3` |
| `ready_at`, `failed_at`, `expiring_at`, `expired_at` | State-coupled timestamps |
| `expires_at` | Required, no later than request + 24 hours; generation may only shorten it |
| `last_download_authorized_at` | Optional issuance projection, not proof of completed download |
| `failure_code` | Optional controlled allowlisted code |
| `lock_version` | Required optimistic lock counter |
| timestamps | Required |

The idempotency digest is computed over operation namespace, requester ID, and
the raw HTTP key, so different users may safely choose the same client key. The
field, filter, idempotency, and request digests use a versioned platform HMAC
key with purpose-separated inputs; plain SHA-256 remains correct only for
checksumming the generated file. The key ring retains every referenced version
for as long as its tombstones are retained; rotation changes the active write
key and never silently destroys the ability to verify historical evidence.

The table uses UUIDv7, indexed foreign keys, unique idempotency digest, status
and due-expiry indexes, digest checks, JSON type/cardinality checks, nonnegative
count checks, maximum-attempt checks, ordered expiry, and complete state/timestamp
checks. `field_keys` and `filters` are required in active states and must be SQL
`NULL` in `expired`; their digests remain required in every state.

The model has exactly one private Active Storage attachment:

```ruby
has_one_attached :file, service: :private_exports
```

Production `private_exports` storage must be non-public cloud/object storage with
provider encryption at rest and public ACLs disabled. Production boot/deployment
validation rejects Disk storage when attendee exports are enabled. Test/local
Disk services remain private and deterministic but are not evidence of provider
encryption.

## State and recovery

```text
pending -> processing -> ready
                     \-> failed
pending/processing/ready/failed -> expiring -> expired
```

A worker claims `pending`, or reclaims `processing` whose 15-minute lease is
stale, while holding the export row lock. Only one attempt number wins. A retry
purges any partial attachment before regenerating. After three failed attempts,
the row remains controlled `failed` until normal expiry.

### Synchronization contract

Every export state-changing transaction and every source-answer erasure
transaction acquires the same transaction-scoped PostgreSQL advisory lock first:

```ruby
Core::Database::AdvisoryLock.acquire!("registration-privacy-event", event.id)
```

The existing retention scope locks still serialize legal-hold placement/release
against eligibility and erasure. The shared event privacy lock closes the
additional export boundary, while per-export row locks and monotonic states
serialize individual export attempts. The lock is held only for short database
transactions; CSV generation and object upload always happen outside it.

The required protocol is:

1. request/replay resolution acquires the event privacy lock before inserting or
   reading the idempotent export row;
2. generation claim/reclaim acquires the event privacy lock, then the export row,
   and releases both before producing/uploading the file;
3. source erasure acquires all affected event privacy locks in ascending event-ID
   order, then locks active exports in ascending export-ID order and changes them
   to `expiring` before clearing answer/revision ciphertext;
4. generation finalization reacquires the event privacy lock, then the export row,
   and may write `ready` only when status is still `processing` and the claimed
   attempt still matches; and
5. download authorization and expiry/invalidation follow the same event-lock-
   before-export-row-lock order before checking or changing state.

A worker that starts from an export ID may read immutable `event_id` without a
row lock, acquire the advisory lock, then lock and reload the export. It must
never hold an export row lock while waiting to acquire the event lock. If the row
vanishes or the reloaded event ID differs, the command fails safely.

If finalization commits first, invalidation subsequently moves `ready` to
`expiring` and queues purge before source erasure commits. If invalidation commits
first, finalization observes `expiring` and purges its partial artifact instead of
restoring `ready`. A concurrent new request either commits before erasure obtains
the shared lock and is included in invalidation, or waits for erasure to commit
and can read only post-erasure answer state. It cannot commit in the invalidation
gap. These race directions, lock ordering, and download versus invalidation
require independent-connection PostgreSQL tests.

`expiring` immediately blocks status-based download authorization. Remote object
deletion happens outside the database transaction and is retryable. Only after
the attachment/blob is gone does `Expire` clear `field_keys`/`filters`, set
`expired`, and retain digests and audit metadata. A stuck `expiring` row is
reprocessed by the recurring expiry job.

## Request flow and idempotency

`POST /events/:event_id/attendee_exports` requires the HTTP
`Idempotency-Key` header and accepts `row_mode`, normalized selectors, bounded
filters, reason code, and an optional request-purpose reauthentication proof.
The proof becomes mandatory only after the command determines that the request is
not an exact replay.

Inside one transaction, `Ticketing::Exports::Request`:

1. acquires the shared `registration-privacy-event` advisory lock;
2. authenticates and reauthorizes the current actor, event, and every selector;
3. validates and canonicalizes event-owned ticket-type/date/status filters;
4. computes scoped `idempotency_key_digest`, canonical `request_fingerprint`,
   `field_set_digest`, and `filter_digest`;
5. resolves the idempotency key before accessing the proof and returns an
   existing matching request without requiring, reading, validating, or consuming
   another proof and without publishing another audit/outbox event;
6. rejects the same key with different actor/event/row mode/fields/filters/reason;
7. only for a genuinely new request, requires and atomically consumes a valid
   request-purpose proof;
8. creates `pending` with `data_cutoff_at = Time.current` and a maximum 24-hour
   expiry; and
9. writes `Core::Audit::Record` plus `Core::Outbox::Publish` for
   `ticketing.attendee_export.requested` in the same transaction.

The Ticketing outbox handler enqueues `GenerateAttendeeExportJob` with only the
export ID. Duplicate outbox delivery and duplicate jobs are safe.

The controller must pass an optional raw proof into the command rather than call
`params.require` for it. This preserves safe retries after the original proof's
five-minute lifetime. Authentication, current policy authorization, canonical
request parsing, and fingerprint comparison still run on every replay; only
proof presence/validation/consumption and new side effects are bypassed. A key
reused with a different fingerprint returns `idempotency_conflict` regardless of
the supplied proof.

## Generation and retention interaction

`data_cutoff_at` is an upper bound for source-row existence, not a claim that an
asynchronous job holds a database snapshot open from request time. Generation
includes only registrations created by the cutoff and only effective answers and
revisions that:

- belong to the event and the submitted immutable form version;
- have an original `answered_at <= data_cutoff_at`;
- are not erased;
- have `retain_until` either absent or later than the current generation time;
- are not merely preserved by a legal hold past organizer-visible retention; and
- match the requested selectors and filters.

Mutable registration lifecycle fields, canonical registration-user contact, and
authorization are intentionally read at generation time. Therefore a status
filter uses the current status of the cutoff-bounded registration cohort and the
contact selectors use current user values; append-only answer content still uses
the cutoff below.

The selected effective revision is the highest non-erased revision whose
`revised_at <= data_cutoff_at`; otherwise the eligible original is used. Before
ready transition, generation shortens `expires_at` to the earliest non-null
`retain_until` represented in the artifact and rejects an already-expired result.

Generation writes fields in registry order and rows in deterministic
`(registration_id, package_unit_number, admission_position)` order. It streams
1,000-row batches to a mode-`0600` binary Tempfile, uses CRLF CSV row separators,
and calculates SHA-256 and byte count over exactly the attached bytes. Cells
whose first character is `=`, `+`, `-`, `@`, tab, or carriage return are prefixed
with a single quote so spreadsheet software treats attendee content as text.
Arrays use canonical JSON. Nil is empty. Dates use ISO 8601.

After upload, generation locks the export again. It finalizes `ready` only if
the row is still `processing`, the attempt matches, the actor remains authorized,
the attachment exists, no limit was exceeded, and the export has not been
invalidated. Otherwise it purges the attachment and records a controlled failure.
Plaintext Tempfiles are closed and unlinked in `ensure`; abrupt process death is
handled by operating-system temp cleanup and the stale-attempt recovery path.

Every answer-erasure path calls `Ticketing::Exports::InvalidateForEvent` inside
the same transaction before clearing ciphertext. It locks active exports for
the event in ID order, changes them to `expiring`, and publishes one idempotent
`ticketing.attendee_export.purge_requested` outbox event per export before
allowing erasure to commit. Its handler enqueues `PurgeAttendeeExportJob` with
only the export ID. Processing workers therefore cannot finalize a now-invalid
export. This conservatively invalidates the whole event's active exports; launch
does not add a per-answer export-manifest table.

## Download authorization and signed-URL limitation

`GET /attendee_exports/:id` returns lifecycle metadata only to the requester or
platform administrator after current authorization. There is no artifact URL in
the serializer.

`POST /attendee_exports/:id/download_authorizations` requires a fresh
`attendee_export_download` proof in the request body. Inside one transaction,
`AuthorizeDownload` locks/reloads the export, verifies `ready` and
`Time.current < expires_at`, reauthorizes every field, atomically consumes the
proof, sets `last_download_authorized_at`, and writes
`Core::Audit::Record(action: "ticketing.attendee_export.download_authorized")`.
After commit it returns a private attachment URL whose lifetime is the lesser of
two minutes and the remaining artifact lifetime.

The URL is a short-lived bearer capability and may be a provider pre-signed URL.
Digis audits authorization issuance, not confirmed byte completion. Authorization
cannot be revoked after issuance except by object deletion, which may have
provider propagation delay. This bounded two-minute limitation is accepted for
launch. A future requirement for immediate revocation or confirmed-download
auditing must use an authenticated application proxy or envelope-encrypted file
with key revocation.

## Expiry and tombstones

The recurring job claims due `pending`, `processing`, `ready`, `failed`, and
stuck `expiring` rows in bounded `FOR UPDATE SKIP LOCKED` batches. `Expire`:

1. transitions an active row to `expiring`, blocking new download authorization;
2. purges the attachment/blob with retry-safe behavior;
3. clears `field_keys`, `filters`, `failure_code`, and any filename/content-type
   projection;
4. sets `expired_at` and `status = expired`; and
5. writes a synchronous, idempotent expiry audit without request payload.

The tombstone retains event, requester, row mode, format version, reason,
versioned keyed digests, row count, checksum, cutoff, lifecycle times, and audit
references. It contains no selectors, filters, answers, or artifact; request
matching remains possible only through the controlled HMAC service.

## Error handling

Expected failures return `Core::Result.failure` with stable business errors:

- `invalid_reauthentication_proof`: `401` for missing, invalid, expired, used,
  wrong-purpose, or wrong-session proof on a genuinely new request or download
  authorization; an exact request replay never evaluates this input;
- `missing_idempotency_key`: `400`;
- policy failure: `403`;
- invalid selector, selector conflict, row mode, sensitivity, reason, or filter:
  `422`;
- `idempotency_conflict`: `409`;
- `export_not_ready` or `export_expired`: `409`/`410` respectively;
- `export_too_large`, `export_generation_failed`, or `export_storage_unavailable`:
  controlled non-payload failures.

Unexpected programmer/infrastructure errors raise into the existing rescue and
job retry layers. Logs contain IDs and controlled codes only. Parameter filters
cover password, proof, selectors, filters, answers, email, phone, token, URL, and
idempotency headers. Raw exceptions never enter `failure_code`, audits, or outbox
payloads.

## Audit contract

Use `Core::Audit::Record` synchronously for request creation, generation ready or
terminal failure, download authorization, invalidation, and expiry. Stable audit
keys make retries idempotent. Allowed metadata contains export/event/requester
IDs, status transition, digests, row count, byte count, attempt number, and
controlled failure/reason codes. It never contains selectors, filters, contact
values, answers, proof/session digests, URLs, filenames, or legal content.

## Testing and phase gate

Test-first implementation must prove:

- authenticated password verification, JTI binding, five-minute expiry, purpose
  binding, login-grade throttling, generic failure, single atomic consumption,
  deactivation/revocation, and concurrent use;
- exact request replay with omitted, expired, consumed, or malformed proof and no
  proof read/validation/consumption, plus mismatched replay conflict;
- owner/admin/manager authorization, requester-only visibility, platform-admin
  override, staff/scanner denial, and unrelated-event denial;
- standard/contact/dietary/accessibility permission separation;
- registration and admission row modes, group package coordinates, historical
  question compatibility, conflicting question definitions, and explicit
  registration-user contact repetition without implying a slot attendee;
- event-owned ticket-type/access-date/status filters and selector/row/byte limits;
- fixed cutoff, effective-revision selection, erased/expired exclusion, legal
  hold non-exportability, and earliest-retention expiry cap;
- durable outbox generation, duplicate delivery, stale lease reclaim, partial
  attachment cleanup, maximum attempts, and no stuck processing rows;
- deterministic CSV bytes, formula neutralization, checksum, row count, and
  private `private_exports` service;
- retention erasure invalidating pending/processing/ready exports before
  ciphertext removal;
- POST download authorization, fresh proof, reauthorization, audit, URL TTL cap,
  and absence of URLs from serializers;
- expiring retries, blob purge, selector/filter clearing, and payload-free
  tombstone;
- PostgreSQL constraints and real independent-connection concurrency tests; and
- shared event privacy advisory locking, global event/export lock order, both
  finalization/invalidation directions, and new-request/erasure serialization.

Verification includes focused model/service/policy/job/integration tests, the
